# Held-out attack split — version 1
#
# The ids listed here are SEALED. They are excluded from the development corpus
# the firewall is built and tuned against, so that tasks 51 and 52 can measure
# the firewall on attacks it was never shaped by. A detection rate over the
# development set alone measures how well the firewall fits what it has already
# seen; a rate over this set measures whether that fitting generalises.
#
# The rules that keep the number honest:
#   - Nothing in this file may be read while building or tuning a detector.
#     The whole point is that these documents are unseen. A detector designed
#     against a held-out document has quietly turned it back into training data.
#   - This split is versioned. When it changes, the version changes, and any
#     measurement citing it names the version. "Measured against held-out v1"
#     is a claim someone can reproduce; "measured against the held-out set" is
#     not, once the set has moved.
#   - One attack per family, chosen by id alphabetically — a rule a machine
#     applies, not a judgement someone makes looking at the contents. Every
#     family is represented, so the split can report whether generalisation
#     holds per family rather than only in aggregate.
#
#
# Each id carries the sha256 of its attack, over the payload *and* its
# expected outcome. That is what makes this a seal rather than a list:
# "held out" was otherwise a promise that these files were not read while
# tuning, which nothing checked and which editing one of them quietly
# broke — including editing `expect: detected` to `expect: undetected`
# after a disappointing run. `verify_seal` fails the load when one changes.
#
# Format: one attack id per line, `<family>/<slug>  sha256:<hex>`.
# Blank lines and #-comments are ignored.
