Sixteen assertions against a real Keycloak, from outside every container.
=========================================================================

Captured verbatim from the `image · compose · smoke` job of CI run 31297776672
(PR #28, task 30). Reproduce with:

    make up
    make identity-smoke

Why this file exists
--------------------

Every identity test in this repository before task 26 validated a token this
repository signed, against a key set this repository served, from an issuer this
repository invented. That proves the code is self-consistent. It cannot prove
the code is right — a mock that agrees with your client proves only that you
wrote both.

This is the same system with a real authorization server on the other end, a
committed realm, two invented users, and a gateway that has never seen any of
it before the container started.

The six lines worth reading twice
---------------------------------

**"a genuine token from an untrusted authorization server is refused."**
Not a forgery and not a tampered signature: a real, correctly signed, unexpired
token, minted moments earlier by Keycloak's own `master` realm — an
authorization server this gateway simply never agreed to trust. ADR 0016 argues
that pooling trusted keys and reading `iss` afterwards lets one server mint
another's principals. This is that argument checked against something that did
not come out of this repository.

**"the upstream did NOT receive the caller's token."**
The invariant the whole security model rests on, observed from outside the
gateway process. Every other assertion of it in this repo inspects a request the
gateway built, using the same code path that builds it. This one asks the
upstream what actually arrived: the mock fleet reports a SHA-256 fingerprint of
the credential it was handed, and it does not match the fingerprint of the token
alice presented. Two independent observations of the same claim.

**"the credential names exactly one upstream."**
`aud=['acp-upstream-mock-a']`, and mock-b's says `acp-upstream-mock-b`. A token
minted for one upstream is useless against its neighbour, so an upstream that is
compromised — or merely curious — cannot replay what it was given. That is the
confused-deputy defence, and it is what RFC 8707 resource indicators exist for.

**"the credential still names the human it was minted for."**
`sub` is alice's Keycloak subject; `actor` is `acp-gateway`. Delegation, not
impersonation. An exchanged token whose subject had become the gateway would
have thrown away the only thing this entire phase exists to preserve — the
upstream's ability to log *who the work was actually for*. Keycloak's standard
token exchange emits no RFC 8693 `act` claim of its own, so the committed realm
adds it with a hardcoded mapper; this line is that workaround being checked
rather than assumed.

**"neither credential is valid at the other upstream."**
Added in task 28, and the reason it is a separate line from the one above is
that RFC 8707's `resource` parameter — the specified way to ask for exactly this
— is accepted and silently discarded by this server (`make probe-resource`,
ADR 0020). Asserting that the parameter was *sent* would pass against a server
that throws it away. This asserts the property instead: the two audiences do not
intersect, so a compromised mock-a holds nothing that works at mock-b.

**"a second caller is not served the first one's credential."**
Added in task 30, and it is the only line here that guards against a mistake
this repository would otherwise have made on purpose. Credentials are now held
between calls, and what is held is naturally described as "the credential for
mock-a" — so keying the cache on the upstream is the obvious design. It is also
a privilege escalation: bob's call arrives at mock-a holding a credential whose
`sub` is alice. It is fast, it returns data, every functional test passes, and
the only artefact is a line in the upstream's audit log attributing bob's read
to alice.

So the key is the *request* — a digest of the subject token, the audience and
the resource — rather than a model of it (ADR 0022). This line is that key
checked from the one place the leak would be a fact rather than an inference:
two fingerprints, two subjects, at the same upstream.

Its partner, **"a repeat call reuses the cached credential"**, is the check for
the opposite and quieter failure. A key that is too *specific* never hits,
returns entirely correct credentials, breaks nothing, and silently sends every
request to the authorization server. No test of correctness would report it.

Notes
-----

`***` on the second line is GitHub Actions' own log masking, not the gateway's.
The header reads `Bearer resource_metadata="…"`.

The subject is a Keycloak UUID rather than `alice@example.test` because
`sub` in an OIDC token is the stable internal identifier, not the username —
which is the correct thing for an upstream to key on, since usernames change.

`tools/call` rather than `tools/list` in the last eight checks, deliberately.
With the health prober running, the catalogue cache is permanently warm and a
`tools/list` may never reach an upstream at all — the same property that made
the request-path fan-out invisible in traces until probing was turned off.

Alice's credential fingerprint is `c79dd22d402f1ddb` in three separate checks —
10, 15 and 16 — each of which makes its own `tools/call`. Before task 30 those
would have been three different strings, because each call minted its own
credential. The cache is visible here in a line nobody wrote an assertion for.

Identical fingerprints are evidence of a cache hit rather than a coincidence
only because Keycloak puts a `jti` in every token it mints: two fresh exchanges
for the same caller and the same upstream are still two different strings.
